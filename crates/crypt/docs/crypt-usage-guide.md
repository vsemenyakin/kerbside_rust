# Крейт `crypt`: как подключить к своему проекту

Гайд для программиста, который видит этот крейт впервые. Здесь по шагам, с
командами, которые можно копировать. Ничего заранее знать не нужно.

---

## Что делает `crypt` (в двух словах)

Прячет от чужого «реверс-инжиниринга» две вещи в вашем скомпилированном бинаре:

1. **Числа-константы** (пороги, коэффициенты, калибровку) — чтобы их нельзя было
   просто вычитать из файла.
2. **Строки-сообщения** (тексты ошибок) — чтобы они не «светились» в бинаре.

И, по желанию, добавляет третий уровень:

3. **Привязку расшифровки к неизменности кода** — если кто-то пропатчит ваш
   бинарь (вставит «жучок») или запустит его в эмуляторе, всё расшифруется в
   мусор.

Уровни включаются по нарастающей. Начните с уровня 1 — это буквально две строки.

> **Что нового по сравнению с ранними версиями крейта** (на случай, если вы уже
> пользовались `crypt`):
> - каждая константа теперь шифруется **своим под-ключом** (зависит от места
>   вызова макроса) — вскрытие одной не расшифровывает остальные; это происходит
>   автоматически, менять в коде ничего не надо;
> - для боевой сборки можно подставить **случайный ключ на каждую сборку** через
>   переменную окружения `CRYPT_K` (см. отдельный раздел ниже);
> - ключ уровня 3 больше **не хранится собранным в одной переменной** — он
>   пересобирается из частей прямо в точке расшифровки, так что «снять его одной
>   точкой останова» уже нельзя (детали — в разделе «Пределы»).

---

## Шаг 0. Подключить крейт

Проще всего иметь `crypt` как локальный крейт рядом с вашим проектом (папка
`crates/crypt`). Тогда в вашем `Cargo.toml`:

```toml
[dependencies]
crypt = { path = "crates/crypt" }
```

> Добавьте крейт в члены workspace — это **обязательно**, если планируете уровень 3
> (шаг `seal` выбирает пакет по имени: `cargo run -p crypt --bin seal`). Для
> уровней 1–2 не требуется, но и не мешает:
> ```toml
> [workspace]
> members = [".", "crates/crypt"]
> ```
> Если секции `[workspace]` нет, `crypt` остаётся лишь зависимостью по пути, и
> `cargo … -p crypt` завершится ошибкой `package(s) crypt not found in workspace`.

> Крейту нужен Rust **1.80+** (edition 2021). Проверить: `rustc --version`.

Проверьте, что собирается:

```bash
cargo build
```

Если собралось — вы готовы к уровню 1.

## Уровень 1 — прятать числа (2 минуты, ничего настраивать не надо)

Оборачивайте числовые константы в макросы:

```rust
// было:
let scale = 1.35;
let max_count = 48;

// стало:
let scale = crypt::encf!(1.35);      // для дробных (f64)
let max_count = crypt::enci!(48);    // для целых (i64)
```

В коде читается как обычное число, но в бинарь попадает зашифрованный вид, а
расшифровка происходит «на лету» в момент использования. Каждое такое число
шифруется **своим** под-ключом (зависит от строки и столбца вызова), поэтому даже
если атакующий вскроет одно значение, остальные это ему не раскроет.

**⚠️ Единственное правило:** внутри `encf!`/`enci!` можно писать только
**литералы или константы** — то есть `1.35`, `48`, `i64::MAX`. Нельзя передавать
переменную:

```rust
let x = 1.35;
let y = crypt::encf!(x);   // ❌ НЕ СКОМПИЛИРУЕТСЯ
let y = crypt::encf!(1.35);// ✅ так правильно
```

Всё. Никаких фич, никаких шагов сборки. Уже работает.

**Как убедиться, что число спрятано:** соберите проект и поищите его в бинаре —
его там не должно быть в открытом виде:

```bash
cargo build --release
strings target/release/ваш_бинарь | grep 1.35   # ничего осмысленного
```

## Уровень 2 — стирать строки-сообщения

Для текстов, которые не нужны в «боевом» бинаре (сообщения об ошибках):

```rust
return Err(crypt::obfstr_err!("cannot open the config file"));
```

Поведение зависит от того, включена ли фича `redact`:

- **без `redact`** (обычная сборка) — строка зашифрована, но остаётся (удобно
  отлаживать);
- **с `redact`** (боевая сборка) — строка **исчезает** совсем (превращается в
  `""`), в бинарь не попадает.

Как включать `redact` — в следующем разделе (это делается вместе с уровнем 3).

---

## Уровень 3 — привязка к неизменности кода (`self-integrity`)

Самый сильный уровень. Тут появляются требования и **обязательный шаг после
сборки** — «запечатывание» (`seal`).

### Как это работает (в двух словах)

Ключ расшифровки на запуске собирается по формуле
`ключ = размер_страницы ^ хеш(.text) ^ SALT2`, где `хеш(.text)` — «отпечаток»
вашего собственного кода. Шаг `seal` после сборки прописывает в бинарь такое
значение `SALT2`, чтобы ключ сошёлся в правильный **только** на подлинном,
непропатченном коде и на нужном железе. Пропатчили байт кода → хеш поехал → ключ
неверный → все `encf!`/`enci!`/`obfstr_err!` расшифровываются в мусор. Запустили
под эмулятором, который подменяет размер страницы → та же «безопасная» поломка.

### Что нужно знать заранее

| Требование | Пояснение простыми словами |
|---|---|
| **Только Linux, бинарь PIE** | Механизм читает служебную информацию Linux-бинаря. На Windows/Mac он просто ничего не делает (безопасно). PIE — это стандарт для современных бинарей, обычно уже так. |
| **Знать размер страницы целевой машины** | Узнать: `getconf PAGESIZE`. Обычно **4096** (x86/большинство arm), на Raspberry Pi 5 — **16384**. |
| **Две сборки: обычная и боевая** | `self-integrity` включайте **только** в финальной сборке. Если включить всегда — обычные сборки будут выдавать мусор, пока их не «запечатали». |

### Настройка (делается один раз)

В вашем `Cargo.toml` заведите свою фичу «боевой сборки», которая включает фичи
крейта. **Не включайте их по умолчанию:**

```toml
[features]
# включаем только для финальной, «боевой» сборки
harden = ["crypt/self-integrity", "crypt/redact"]
```

### Использование в коде

Самым первым делом в `main` вызовите `init_keying()`:

```rust
fn main() {
    crypt::init_keying();   // без self-integrity это ничего не делает (безопасно)

    // ... дальше ваш код, где используются encf!/enci!/obfstr_err!
}
```

> Почему первым: `init_keying` собирает ключ расшифровки. Если вызвать его после
> первого `encf!`, расшифровка не сработает.

### Сборка «боевого» бинаря — три команды по порядку

```bash
# 1) собрать с включённой защитой
cargo build --release --features harden

# 2) (опционально) убрать символы — как для любого релиза
strip target/release/ваш_бинарь

# 3) ЗАПЕЧАТАТЬ — обязательно ПОСЛЕДНИМ шагом, после strip.
#    --page-size = размер страницы вашей ЦЕЛЕВОЙ машины (getconf PAGESIZE)
cargo run -p crypt --bin seal -- target/release/ваш_бинарь --page-size 4096
```

> **Почему `seal` последним:** он считает «отпечаток» готового кода. Любое
> изменение бинаря после этого сломает отпечаток. Поэтому запечатывание — самый
> последний шаг.
>
> **Если пропустить шаг 3** — бинарь запустится, но выдаст мусор. Это защита «в
> безопасную сторону»: незапечатанный бинарь не работает «наполовину».
>
> **Если ваш релиз собирается особым тулчейном** (например, обфускатором через
> `RUSTC_WORKSPACE_WRAPPER`) — соберите `seal` **обычным** тулчейном отдельно,
> чтобы инструмент запечатывания не был обфусцирован сам:
> ```bash
> env -u RUSTFLAGS -u RUSTC_WORKSPACE_WRAPPER cargo build -p crypt --bin seal
> ./target/debug/seal target/release/ваш_бинарь --page-size 4096
> ```

### Проверка

```bash
# обычная (отладочная) сборка — работает и отлаживается как обычно:
cargo build && ./target/debug/ваш_бинарь

# боевая, запечатанная — работает на целевой машине:
./target/release/ваш_бинарь
```

## Случайный ключ на каждую сборку (`CRYPT_K`) — рекомендуется для поставки

Базовый ключ шифрования `encf!`/`enci!` по умолчанию — фиксированная (не «магическая»)
константа, зашитая в крейт. Для разработки этого достаточно. Но у **боевой**
сборки лучше, чтобы ключ был **свой на каждую сборку** — тогда две поставки не
делят один и тот же ключ, и «узнать ключ один раз — расшифровать все версии» не
работает.

Крейт читает ключ из переменной окружения `CRYPT_K` **на этапе компиляции**
(через `option_env!`). Задайте её случайным 64-битным числом при сборке:

```bash
# случайный ключ на эту сборку (десятичный или 0x-hex; допускаются подчёркивания)
CRYPT_K="0x$(od -An -N8 -tx1 /dev/urandom | tr -d ' \n')" \
  cargo build --release --features harden
```

- переменная **не задана** → берётся фиксированный дефолт (нормально для dev);
- переменная **задана** → это значение впекается в бинарь как ключ.

> `CRYPT_K` влияет только на **ключ шифрования**, а не на расшифрованные значения:
> при любом ключе `encf!(1.35)` в рантайме даёт те же `1.35`. Поэтому менять
> `CRYPT_K` между сборками безопасно — поведение программы не меняется.

Итоговый порядок для боевой сборки со случайным ключом:

```bash
CRYPT_K="0x$(od -An -N8 -tx1 /dev/urandom | tr -d ' \n')" \
  cargo build --release --features harden
strip target/release/ваш_бинарь
./target/debug/seal target/release/ваш_бинарь --page-size 4096   # seal — последним
```

## Чек-лист частых ошибок

- [ ] `encf!`/`enci!` получают **литерал**, а не переменную.
- [ ] `crypt::init_keying()` вызван **самым первым** в `main`.
- [ ] `self-integrity`/`redact` включены **только** в боевой сборке (через свою
      фичу `harden`), а не по умолчанию.
- [ ] (Для поставки) на боевую сборку подставлен случайный `CRYPT_K`.
- [ ] Шаг `seal` — **последний**, после `strip` и любых других правок бинаря.
- [ ] `--page-size` совпадает с размером страницы **целевой** машины
      (`getconf PAGESIZE` на ней).
- [ ] Боевой бинарь запускается **на том же типе железа**, под который
      запечатан (иначе — мусор: это часть защиты).

## Полный минимальный пример

**`Cargo.toml`:**
```toml
[package]
name = "myapp"
version = "0.1.0"
edition = "2021"

# Нужно, чтобы шаг seal мог выбрать пакет по имени: cargo run -p crypt --bin seal
[workspace]
members = [".", "crates/crypt"]

[dependencies]
crypt = { path = "crates/crypt" }

[features]
harden = ["crypt/self-integrity", "crypt/redact"]
```

> **`seal` работает только на Linux/ELF.** Уровень 3 (`self-integrity` + `seal`) —
> для Linux-бинарей (PIE/ELF). На Windows/Mac `self-integrity` — no-op, «отпечатка»
> `SALT2` в бинаре нет, а `seal` парсит именно ELF (на PE-`.exe` он выдаст
> `not a 64-bit ELF`). Поэтому боевую сборку с `harden`/`seal` запускай **на Linux**
> (в т.ч. кросс-таргет). На других ОС для разработки достаточно уровней 1–2 — они
> кроссплатформенные и `seal` не требуют.

**`src/main.rs`:**
```rust
fn main() {
    crypt::init_keying();

    let scale = crypt::encf!(1.35);
    let limit = crypt::enci!(90);

    if some_error_condition() {
        eprintln!("{}", crypt::obfstr_err!("configuration is invalid"));
        std::process::exit(1);
    }

    println!("scale={scale} limit={limit}");
}

fn some_error_condition() -> bool { false }
```

**Обычная сборка (для разработки):**
```bash
cargo run
```

**Боевая сборка (для поставки, на Linux):**
```bash
CRYPT_K="0x$(od -An -N8 -tx1 /dev/urandom | tr -d ' \n')" \
  cargo build --release --features harden
strip target/release/myapp
cargo run -p crypt --bin seal -- target/release/myapp --page-size 4096
./target/release/myapp
```

## Если нужен только уровень 1–2

Тогда всё ещё проще: **не** включайте фичу `harden`, не вызывайте `seal`, не
думайте про размер страницы и `CRYPT_K`. Просто:

1. `crypt = { path = "crates/crypt" }` в зависимостях;
2. оборачивайте числа `encf!/enci!`, а сообщения — `obfstr_err!`.

Никаких требований к платформе и шагов сборки.

---

## Пределы (чтобы не переоценивать)

`crypt` **сильно поднимает стоимость** статического анализа, но это не «серебряная
пуля»:

- От **дампа памяти** запущенного процесса с правами root он не спасает —
  расшифрованные значения там видны. Ключ уровня 3 теперь не лежит собранным в
  одной переменной (пересобирается из частей в точке расшифровки), поэтому «снять
  его одной аппаратной точкой останова» уже нельзя — но упорный атакующий с root и
  живым отладчиком по-прежнему всё достанет. Анти-отладка и анти-дамп — это
  **отдельные меры вашего приложения** (self-ptrace, `PR_SET_DUMPABLE`, `mseal`,
  детект инъекций), в этот крейт они не входят.
- Против **очень упорного** реверсера, который разберёт схему до конца, ключ в
  теории вычислим. Крейт делает это дорогим, а не невозможным.
- `crypt` занимается только константами, строками и привязкой ключа. Он **не**
  убирает символы, **не** обфусцирует поток управления и т.п. — это отдельные
  меры вашего проекта.

Самая надёжная защита числа — **вообще не класть его в боевой бинарь** (например,
свернуть порог в веса нейросети/калибровку на этапе сборки). Чего в файле нет — то
никаким анализом не достать. Единственная по-настоящему устойчивая к root защита —
**аппаратный корень доверия** (TrustZone/secure element), где секрет не появляется
в обычной памяти процесса.
